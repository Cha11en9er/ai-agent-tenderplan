# Оркестратор OpenCode: один полный цикл по одному тендеру

Запускай в **[OpenCode](https://opencode.ai)** в каталоге проекта **`C:\repos\YouDo\ai-agent-tenderplan`** (рабочая директория сессии = корень репозитория).

**Каркас для любого числа тендеров** (пакет из K, два запуска браузера на весь пакет и т.д.) — в **`prompt_pipeline_agent.md`**. Этот файл — только сценарий **ровно одного** id после парсинга.

Ты **сам выполняешь весь пайплайн**: команды в терминале, чтение/запись файлов, анализ по правилам RV42. Пользователь даёт один запрос вроде: «выполни пайплайн из `prompt_pipeline_agent_one.md` для одного тендера».

**Не задавай пользователю уточняющих вопросов** (в т.ч. «какой id выбрать»). При любой неоднозначности действуй по **жёстким правилам ниже** и в конце только **отчитайся**, что сделано.

**Обязательно опирайся на критерии** из **`prompt_tender_analyzer_new.md`** (профиль ≥ 60 %, себестоимость/маржа, метки ✅⚠️🟡, очистка диска после успешной записи JSON).

## Ровно два запуска Chromium на один полный цикл (не путать)

На **один** тендер от «старта парсера» до «метка и комментарий на сайте» полагается **два отдельных** запуска Playwright, **последовательно**:

1. **Фаза 1** — `mian_parse_exactly_key.py`: браузер открывается и закрывается здесь. Внутри: сбор данных, скачивание файлов, служебная метка парсера (**«На анализе»** или значение из **`runtime_settings.json`** / `TENDER_DONE_MARK_TEXT`).
2. **Фазы 2–4** — **без браузера** (файлы, JSON, рассуждение модели).
3. **Фаза 5** — `mark_tender.py`: **новый** запуск браузера. Комментарий **`platform_comment`** и финальная метка **«Подходит»** / **«Не подходит»**.

**Не нужно:** открывать сайт вручную между фазами, второй раз гонять парсер перед меткой, держать два окна Chromium одновременно от разных скриптов. Если кажется, что «окон слишком много» — это обычно как раз эти **два** прогона подряд; третье окно без причины — ошибка.

---

## Терминал (OpenCode): как запускать команды

- **Не оборачивай** цепочку в `powershell -Command "..."` — при экранировании ломается `$env:` и аргументы.
- Запускай команды **в той оболочке, которую даёт OpenCode** (обычно уже PowerShell), **построчно** или одним многострочным блоком **без вложенного `powershell -Command`**.
- Парсер одного тендера: после `Set-Location` и `Activate.ps1` обязательно  
  `python .\mian_parse_exactly_key.py --process 1`  
  (`--process 1` перекрывает лимит из **`runtime_settings.json`** и `.env`).
- Чтобы сменить ключ списка или метку парсера **по указке из промпта**, правь **`runtime_settings.json`** (не `.env`). В `.env` только **`LOGIN`** и **`PASSWORD`**.

## Как пользователь стартует в OpenCode

1. Открыть проект: папка `ai-agent-tenderplan`.
2. В чат агента вставить задачу и приложить этот файл и **`prompt_tender_analyzer_new.md`** (при пакете из нескольких тендеров дополнительно **`prompt_pipeline_agent.md`**). Или указать пути `@prompt_pipeline_agent_one.md` и `@prompt_tender_analyzer_new.md`.
3. Убедиться, что агент может вызывать **PowerShell** из корня репозитория.

## Условия

- **`.env`**: только **`LOGIN`** и **`PASSWORD`** (шаблон: `.env.example`).
- **`runtime_settings.json`**: ключ сайдбара, лимиты, текст метки парсера и т.д. — при необходимости агент **редактирует этот файл** до или между запусками по задаче пользователя.
- Есть **`venv`**, зависимости и **`playwright install chromium`**.
- **`auth.json`** желателен (если нет — парсер выполнит вход сам).

## Фаза 0 — зафиксировать состояние до парсинга

Перед парсером запомни список каталогов в **`downloads_recognize\`** (имена = прошлые `tender_id`) или время старта — чтобы после фазы 1 однозначно найти **новый** `id`.

---

## Фаза 1 — парсинг ровно одного тендера

Выполни в терминале из корня проекта:

```powershell
Set-Location "C:\repos\YouDo\ai-agent-tenderplan"
.\run_parse_one_tender.ps1
```

Эквивалент без скрипта:

```powershell
Set-Location "C:\repos\YouDo\ai-agent-tenderplan"
.\venv\Scripts\Activate.ps1
python .\mian_parse_exactly_key.py --process 1
```

Дождись завершения (Chromium может открыться и закрыться). Если команда упала — останови пайплайн и опиши ошибку пользователю.

---

## Фаза 2 — определить `tender_id` этого прогона (без вопросов пользователю)

1. Пусть **`before`** = множество имён подкаталогов **`downloads_recognize\`**, зафиксированных в фазе 0.  
2. Пусть **`after`** = то же после фазы 1.  
3. **`новые`** = `after \ before` (по имени каталога = `tender_id`).

Выбор **ровно одного** `<TENDER_ID>`:

- Если **`новые`** пусты — возьми среди каталогов в `downloads_recognize`, у которых есть свежие `.txt`, те **`id`**, которые появились в **`tenders_data.json`** в объектах со **`status`: `анализируем`**, и снова вычти **`before`**. Если всё ещё пусто — возьми **лексикографически минимальный** id среди тех, у кого есть `downloads_recognize\<id>\` с файлами и кто есть в текущем **`tenders_data.json`** (крайний случай).
- Если **`новые`** из **одного** элемента — это `<TENDER_ID>`.
- Если **`новые`** из **нескольких** — это значит прошлый запуск мог обойти лимит или в репозитории уже лежали лишние данные. **Не спрашивай пользователя**: выбери **лексикографически минимальное** имя среди **`новые`** (стабильное правило «взять первый по сортировке»).

В **отчёте (фаза 6)** явно напиши: какие id были в **`новые`**, какой **один** выбран по правилу и что остальные новые каталоги **не трогались** пайплайном (останутся для следующих запусков).

Дальше везде подставляй выбранный `<TENDER_ID>`.

---

## Фаза 3 — анализ (ты же модель-аналитик)

1. Прочитай карточку с этим `id` в **`tenders_data.json`**.
2. Прочитай **`downloads_recognize\<TENDER_ID>\**\*.txt`** (сначала описание объекта, НМЦК, требования, проект контракта).
3. По **`prompt_tender_analyzer_new.md`**: вердикт **`подходит нам`** / **`не подходит нам`**, поля (`review_mark`, `reason_short`, `confidence`, расширенные при необходимости, **`is_marked`: false**). В объект обязательно включай **`platform_comment`** — одна строка вердикта для комментария на Tenderplan (см. блок «Комментарий на платформе» в промпте анализатора); при отсутствии текста скрипт меток подставит **`reason_short`**, но явная строка **`platform_comment`** предпочтительна.
4. **Merge** карточку в **`tenders_accept.json`** или **`tenders_reject.json`** по `id`.
5. **Удали** объект с этим `id` из **`tenders_data.json`**.
6. Проверь валидность JSON после каждой записи.

## Фаза 4 — удалить локальные файлы этого тендера

Только после успешных шагов фазы 3:

```powershell
$base = "C:\repos\YouDo\ai-agent-tenderplan"
$id = "<TENDER_ID>"
Remove-Item -LiteralPath "$base\downloads\$id" -Recurse -Force -ErrorAction SilentlyContinue
Remove-Item -LiteralPath "$base\downloads_recognize\$id" -Recurse -Force -ErrorAction SilentlyContinue
```

По желанию удали **`tenders_dom\<id>.html`**, если есть.

---

## Фаза 5 — комментарий вердикта и метка на Tenderplan только для этого `id`

```powershell
Set-Location "C:\repos\YouDo\ai-agent-tenderplan"
.\venv\Scripts\Activate.ps1
python .\mark_tender.py --only-id "<TENDER_ID>"
```

Скрипт для строк с **`is_marked`: false** **сначала** отправляет на карточку текст из **`platform_comment`** (или **`verdict_message`**, иначе **`reason_short`**), **затем** выставляет метку **«Подходит»** / **«Не подходит»**. В JSON обновится **`is_marked`** у этой строки.

---

## Фаза 6 — отчёт

Кратко: **`TENDER_ID`**, вердикт, **`review_mark`**, текст **`platform_comment`** (что ушло в комментарий на сайте), куда записана карточка, что удалено с диска, итог **`mark_tender.py`** (успех / ошибка: комментарий и метка).

## Про автоматизацию

В OpenCode один агент может связать **терминал + файлы + рассуждение** — отдельный «скрипт без LLM» для шага анализа не обязателен. Если позже понадобится полностью без чата — тогда отдельный сервис с API модели и вызовом тех же Python-скриптов.

---

## Если пайплайн оборвался

- Парсер прошёл, анализ нет: не удаляй **`downloads`** / **`downloads_recognize`**; продолжи с фазы 3.
- JSON записан, метка не встала: выполни **`python .\mark_tender.py --only-id "<TENDER_ID>"`** ещё раз (отсутствие папок с файлами метке не мешает).
